Firecrawl Extract Feature Overview

The 'Extract' feature of Firecrawl is designed to automatically retrieve and structure data from web pages. It enables users to extract specific content such as text, images, metadata, and structured data using customizable parameters. This feature is particularly useful for web scraping, data analysis, and content aggregation tasks.

Firecrawl Fundamentals

1.1 Understanding Firecrawl's Core Functionality

Firecrawl provides an API designed to convert web pages into clean, structured data formats, specifically optimized for use with Large Language Models (LLMs). The primary tool for this is the Scrape API endpoint (POST https://api.firecrawl.dev/v1/scrape). This service handles many underlying complexities inherent in web scraping, such as:

  • Proxy management
  • Data caching
  • Rate limit handling
  • JavaScript rendering
  • Loading dynamic content

This allows developers to focus on utilizing the data rather than managing the intricacies of web page retrieval. You can learn more about the base Scrape API in the API Reference.

Commentary:

Firecrawl positions itself as a developer-centric tool simplifying the often complex process of web data acquisition. Unlike traditional scraping libraries (e.g., Beautiful Soup, Scrapy) that require significant setup for handling JavaScript rendering, proxies, and rate limits, Firecrawl aims to abstract these complexities behind a clean API. For a full-stack developer, this means potentially faster integration and less infrastructure management for data-gathering tasks. The focus on 'LLM-ready' data highlights its relevance in the current AI landscape, where clean, structured input is crucial for effective model performance. Consider Firecrawl as a managed service layer on top of common scraping challenges.

Extract Feature Overview

1.2 Introducing the Extract Feature

The 'Extract' feature is a specialized capability within Firecrawl designed for targeted, structured data retrieval from web pages. It allows users to specify precisely what information they need (e.g., company mission, product prices, contact details) and receive it in a predictable JSON format. This feature is accessible via both the general /v1/scrape endpoint and a dedicated /extract endpoint, offering flexibility depending on the use case. Its core purpose is to simplify the collection of structured data from single pages, multiple URLs, or even entire domains. Find more details on the Extract feature page.

Commentary:

The Extract feature represents a significant step beyond simple content fetching (like retrieving raw HTML or Markdown). It leverages AI (specifically, LLMs) to interpret the content and pull out specific pieces of information according to user-defined instructions (either a schema or a natural language prompt). This capability is particularly valuable for tasks requiring semantic understanding of the page content, not just its structure. For developers building RAG (Retrieval-Augmented Generation) systems or other AI-powered applications, Extract offers a way to directly obtain structured knowledge from web sources, reducing the need for intermediate parsing and structuring steps. Think of it as intelligent, targeted scraping.

Structured Data Extraction Explained

2.1 The Power of Structured Data Extraction

The primary goal of the Extract feature is to retrieve structured data. Instead of just getting the raw text or Markdown of a page, you can define the specific pieces of information you need and their expected format. Firecrawl then uses its capabilities to parse the page content and populate this structure.

You can define the desired structure in two main ways:

  1. JSON Schema: Provide a formal JSON Schema definition outlining the fields, data types (string, boolean, number, etc.), and requirements (e.g., which fields are mandatory).
  2. Natural Language Prompt: Describe the information you want in plain English. The underlying LLM interprets your request and determines an appropriate JSON structure for the output.

This structured approach ensures the output data is consistent and easy to integrate into applications or data pipelines.

Commentary:

Structured data extraction is fundamental for integrating web information into databases, applications, or analytical workflows. Unstructured text (like raw HTML or plain text) requires significant post-processing to be useful programmatically. By providing data in a predefined JSON format (either via a user-supplied schema or an LLM-inferred structure), Firecrawl's Extract feature makes the data immediately actionable. This aligns well with modern development practices favoring well-defined data contracts and API-driven architectures. For a developer working with TypeScript or Rust, the ability to map the extracted JSON directly to typed objects or structs is a significant advantage.

Purpose and Capabilities

2.2 Key Applications and Use Cases

The Extract feature is versatile and supports various data-driven tasks:

  • Web Scraping: Automate the collection of specific data points from websites, such as product information, user reviews, or real estate listings.
  • Data Analysis: Gather targeted datasets from the web for market research, sentiment analysis, or tracking specific metrics across different sources.
  • Content Aggregation: Build applications that consolidate information from multiple websites, like news feeds, job boards, or event listings, by extracting relevant details in a consistent format.

The ability to get structured data directly simplifies these workflows significantly compared to traditional scraping methods that often require manual parser development. Explore more potential applications on the Firecrawl Blog.

Commentary:

These use cases are common drivers for web data extraction tools.

  • Web Scraping: Beyond simple data gathering, structured extraction allows for targeted scraping, like extracting product details (name, price, SKU) from e-commerce sites or contact information from directories. This is more efficient than scraping entire pages and parsing later.
  • Data Analysis: Researchers and analysts can use Extract to gather specific data points from news articles, reports, or social media for trend analysis, market research, or competitive intelligence without manual copy-pasting.
  • Content Aggregation: Platforms that aggregate content (e.g., job boards, news aggregators, price comparison sites) can use Extract to pull standardized information from various sources, ensuring consistency in their own databases and user interfaces. For a full-stack developer, this could power features like automated content updates or competitive monitoring within an application.

Using Extract with /v1/scrape

3.1 Activation via the /v1/scrape Endpoint

One way to use the Extract feature is through Firecrawl's primary scraping endpoint: POST https://api.firecrawl.dev/v1/scrape. This endpoint is designed to convert individual web pages into various clean formats.

To enable structured data extraction using this endpoint, you need to modify the request payload.

Commentary:

Using the /v1/scrape endpoint for extraction integrates this capability into Firecrawl's general-purpose scraping workflow. This might be suitable if you're already using /v1/scrape for other formats (like Markdown) and want to add structured data extraction for the same URL in a single API call. It keeps the interaction pattern consistent if you primarily use this endpoint. However, for tasks focused solely on structured extraction, especially across multiple URLs or domains, the dedicated /extract endpoint might offer a more streamlined interface.

Enabling Extraction in /v1/scrape

3.1.1 The formats Array and extract Parameter

Activation requires two key elements in the JSON request body sent to /v1/scrape:

  1. formats Array: You must include the string "extract" within this array. This tells Firecrawl that you intend to perform structured data extraction.
    {
  "url": "https://example.com",
  "formats": ["extract", "markdown"] 
}
  2. extract Object: When "extract" is present in the formats array, you must also include an extract object in the request body. This object contains the configuration for the extraction process.

As noted in the API Reference, the extract parameter is required if "extract" is in formats.

Commentary:

This mechanism clearly separates the request for standard scraping formats (like Markdown or raw HTML, which might be specified alongside "extract" in the formats array) from the specific configuration for the structured extraction itself. It allows for a modular approach where extraction parameters are only needed when that specific format is requested. This design promotes clarity in the API request structure.

Extraction Configuration (extract Object)

3.1.2 Configuring the extract Object

The extract object is where you define how the structured data should be extracted. It accepts the following fields:

  • schema: A JSON Schema object defining the exact structure (fields, types, requirements) of the desired output JSON. Use this for precise control over the output format.
  • prompt: A natural language string describing the data you want to extract. This is used if the schema field is omitted. The LLM interprets the prompt and determines the output structure itself.
  • systemPrompt (Optional): An additional prompt providing higher-level instructions or context to the LLM to guide its extraction process.
{
  "url": "https://example.com",
  "formats": ["extract"],
  "extract": {
    "schema": { /* Your JSON Schema */ }, 
    // OR
    "prompt": "Extract the main contact email and phone number.",
    "systemPrompt": "Focus only on information present in the footer."
  }
}

Consult the API Reference for detailed specifications.

Commentary:

The choice between schema and prompt offers a trade-off: schema provides predictability and strict structure, ideal for production systems where data consistency is paramount. prompt offers flexibility and is useful for exploratory analysis or when the exact structure isn't known beforehand, but its output might be less consistent. The systemPrompt acts as a meta-instruction, guiding the LLM's behavior during extraction (e.g., specifying tone, focus, or constraints). This is a common technique in prompt engineering to fine-tune LLM outputs.

Using the Dedicated /extract Endpoint

3.2 Activation via the /extract Endpoint

Firecrawl offers a dedicated endpoint specifically for structured data extraction: POST https://api.firecrawl.dev/v1/extract. This endpoint is designed to streamline the process of collecting structured data from one or more URLs, or even entire domains.

It handles the underlying crawling, parsing, and data collation based on your specifications, making it suitable for both small and large-scale extraction tasks. The primary goal is simplification compared to managing multiple /v1/scrape calls. More details are in the /extract API Reference.

Commentary:

The dedicated /extract endpoint (POST https://api.firecrawl.dev/v1/extract) is purpose-built for structured data extraction, especially at scale. It simplifies the API call when extraction is the sole objective. Its ability to handle multiple URLs and domain crawling directly within a single request makes it more convenient than making multiple calls to /v1/scrape. This endpoint likely orchestrates multiple scrape and extraction operations internally, providing a higher-level abstraction for the user.

URL Handling in /extract

3.2.1 Handling Single Pages, Multiple Pages, and Domains

The /extract endpoint is flexible in handling target URLs specified in the urls array parameter:

  • Single Page: Provide a specific URL like https://firecrawl.dev/some-page.
  • Multiple Pages: Provide an array of specific URLs.
  • Full Domain / Multiple Pages with Wildcard: Use a wildcard pattern like https://firecrawl.dev/*. When /* is used, Firecrawl attempts to automatically discover and process all crawlable URLs within that domain.

Important: The wildcard (/*) feature for domain crawling is currently experimental.

{
  "urls": [
    "https://firecrawl.dev/pricing", 
    "https://docs.firecrawl.dev/*" 
  ],
  "extract": { 
    "prompt": "Extract pricing details and main features."
  }
}

Commentary:

The wildcard support (/*) is a powerful feature, essentially turning the extractor into a focused crawler. This is useful for gathering consistent information across a known site structure (e.g., all blog posts, all product pages). However, developers should be mindful of the scope; crawling an entire large domain can be time-consuming and potentially expensive depending on the pricing model. The experimental nature suggests users should monitor performance and results closely. It's crucial to understand the site's structure (robots.txt, sitemaps) when using wildcards to estimate the scope and avoid unintended extensive crawling.

Wildcard Crawling (Experimental)

3.2.2 Wildcard Support and Crawling

The use of /* at the end of a base URL in the urls array triggers Firecrawl's domain crawling capability for the /extract endpoint. Firecrawl will attempt to find and process pages linked within that domain.

As stated in the notes, this feature is experimental. This means its behavior, performance, and coverage might change, and it may have limitations, especially on very large or complex websites. Users should exercise caution and test thoroughly when relying on wildcard crawling. Refer to the /extract API Reference for any updates on this feature.

Commentary:

The experimental status of wildcard crawling implies potential limitations in terms of crawl depth, breadth, speed, and adherence to politeness protocols (robots.txt, crawl delays). Developers using this should implement robust error handling and potentially status monitoring (if using async mode) to manage jobs that might take a long time or encounter issues on complex sites. It's also worth considering the ethical and legal implications of large-scale crawling.

Configuration: Using JSON Schema

4.1 Defining Structure with JSON Schema

When you need the extracted data to conform to a precise structure, you can provide a JSON Schema object within the extract configuration (for /v1/scrape) or the params object (for /extract).

Commentary:

Using a JSON Schema provides the highest level of control and predictability over the extracted data structure. This is crucial for applications where the consuming code expects specific fields and data types. It acts as a contract between the extraction request and the expected output. For developers using statically-typed languages like TypeScript or Rust, defining a schema allows for easy generation of corresponding types/structs, enabling type safety and better developer experience (e.g., autocompletion, compile-time checks). Tools like Pydantic in Python can also leverage schemas for validation.

Defining Schema Fields and Types

4.1.1 Specifying Fields and Data Types

Within the schema object, you define the desired output structure using standard JSON Schema syntax:

  • type: "object": Indicates the root is a JSON object.
  • properties: An object where each key is a desired field name.
    • Each field definition specifies its type (e.g., "string", "boolean", "number", "array", "object").
    • You can add descriptions or other schema keywords as needed.
  • required: An array of strings listing the field names that must be present in the output.
{
  "schema": {
    "type": "object",
    "properties": {
      "company_mission": { 
        "type": "string",
        "description": "The main mission statement of the company."
      },
      "supports_sso": { 
        "type": "boolean" 
      },
      "feature_list": {
        "type": "array",
        "items": { "type": "string" }
      }
    },
    "required": ["company_mission", "supports_sso"]
  }
}

Commentary:

Defining fields and types using JSON Schema standard syntax ensures interoperability and leverages a well-established standard. The required array is particularly important for ensuring essential data points are present in the result, although the LLM's ability to find the data on the page is still a factor. Complex schemas with nested objects and arrays are also possible, allowing for rich data structures.

Example Request with Schema

4.1.2 Example: Schema-Based Extraction Request

Here's an example using cURL to request structured data from https://docs.firecrawl.dev/ using a JSON schema via the /v1/scrape endpoint:

curl -X POST https://api.firecrawl.dev/v1/scrape \
    -H 'Content-Type: application/json' \
    -H 'Authorization: Bearer YOUR_API_KEY' \
    -d '{
      "url": "https://docs.firecrawl.dev/",
      "formats": ["extract"],
      "extract": {
        "schema": {
          "type": "object",
          "properties": {
            "company_mission": { "type": "string" },
            "supports_sso": { "type": "boolean" }
          },
          "required": ["company_mission", "supports_sso"]
        }
      }
    }'

This request asks Firecrawl to find the company mission (as a string) and whether SSO is supported (as a boolean) on the target page, returning them in a JSON object matching the schema.

Commentary:

This cURL example demonstrates a typical API call using schema-based extraction via the /v1/scrape endpoint. Note the Authorization header for the API key and Content-Type set to application/json. The formats array includes "extract", and the extract object contains the schema. This structure is clear and directly maps to the concepts discussed.

Configuration: Using Natural Language Prompt

4.2 Defining Structure with Natural Language

Alternatively, if you prefer not to define a rigid schema, or if you're doing more exploratory extraction, you can use a natural language prompt.

Commentary:

Prompt-based extraction offers flexibility, especially during development or exploration phases. It lowers the barrier to entry as you don't need to construct a formal JSON schema. However, the LLM interprets the natural language prompt, which can introduce ambiguity. The structure of the output JSON is determined by the LLM based on its understanding of the prompt and the page content. This might lead to variations in field names or structure across different runs or different pages, making it potentially less suitable for production systems requiring strict data contracts. It excels in scenarios where the exact output format is less critical than capturing the requested information.

Prompt-Only Extraction

4.2.1 Prompt-Only Extraction Mechanism

When you provide a prompt string within the extract configuration (for /v1/scrape) or params (for /extract) without providing a schema, Firecrawl uses the LLM to:

  1. Understand the information requested in the prompt.
  2. Analyze the content of the target web page(s).
  3. Generate a JSON object containing the extracted information, deciding on the field names and structure itself.

This is useful when you know what data you need but don't want to pre-define the exact JSON format.

Commentary:

This approach relies entirely on the LLM's ability to understand the request and generate a suitable JSON output. The quality of the prompt significantly influences the result. Clear, specific prompts generally yield better outcomes. This method is powerful for quick queries or when dealing with diverse content where a single schema might not fit all pages.

Example Request with Prompt

4.2.2 Example: Prompt-Based Extraction Request

Here's a cURL example using a natural language prompt with the /v1/scrape endpoint:

curl -X POST https://api.firecrawl.dev/v1/scrape \
    -H 'Content-Type: application/json' \
    -H 'Authorization: Bearer YOUR_API_KEY' \
    -d '{
      "url": "https://docs.firecrawl.dev/",
      "formats": ["extract"],
      "extract": {
        "prompt": "Extract the company mission and whether they support SSO."
      }
    }'

In this case, the LLM will determine the best JSON structure to represent the requested information based on the content of https://docs.firecrawl.dev/.

Commentary:

Similar to the schema example, this cURL request targets the /v1/scrape endpoint. The key difference is the extract object now contains only the prompt field. Firecrawl's LLM will process this prompt and return a JSON object, for instance, it might return {"company_mission": "...", "sso_support": false} or a similar structure based on its interpretation.

Optional systemPrompt for Guidance

4.3 Guiding the LLM with systemPrompt

The extract configuration object (for /v1/scrape) or params (for /extract) accepts an optional systemPrompt field. This field allows you to provide additional instructions or context to the underlying Large Language Model (LLM) that performs the data extraction.

For example, you could use systemPrompt to:

  • Specify the desired tone or style of extracted text.
  • Instruct the LLM to focus on specific parts of a webpage.
  • Provide background context that might help interpret the page content.

It serves as a way to guide the LLM's reasoning process during extraction, potentially improving the relevance or accuracy of the results, especially for complex pages or nuanced requests. See the API Reference for usage.

Commentary:

The systemPrompt provides a way to give meta-instructions or context to the LLM performing the extraction, separate from the main prompt or schema. This is useful for guiding the LLM's behavior, such as instructing it to adopt a specific persona, focus on certain sections of the page, ignore irrelevant information, or format the output in a particular style (though schema is better for strict formatting). Effective use of system prompts often involves experimentation to see how they influence the LLM's output for specific tasks and content types. It's a tool for fine-tuning when the default behavior isn't quite right.

Enabling Web Search for Broader Context

4.4 Expanding Scope with Web Search (enableWebSearch)

For the /extract endpoint, you can optionally include the enableWebSearch parameter (boolean) in the request's params object. When set to true, this feature allows the extraction process to potentially follow links found on the initial target pages and incorporate information from those external pages into the final result.

This is useful when the information needed might be spread across multiple related pages or requires broader context than available on the starting URL(s). For instance, extracting product details might benefit from accessing linked review pages.

Python Example Snippet:

data = app.extract([
  'https://nextbase.com/dash-cams/622gw-dash-cam'
], {
  'prompt': "Extract details about the best dash cams including prices, features, pros/cons and reviews.",
  'enableWebSearch': True # Enable web search
})

Check the /extract API Reference for more details.

Commentary:

Enabling web search (enableWebSearch: true) significantly expands the scope of information gathering. Instead of being limited to the content of the initially provided URLs, the extractor can follow links and incorporate information from external pages. This is powerful for tasks requiring broader context, like competitive analysis, product review aggregation, or research synthesis. However, it introduces several considerations:

  • Cost: May increase processing time and potentially API usage costs.
  • Relevance: The system needs to effectively determine which external links are relevant to the original query.
  • Depth/Breadth: The extent of external crawling might be limited.
  • Latency: Extraction will likely take longer. It's best used when the initial pages are known to lack complete information and external context is necessary.

API Response Structure

5.1 Understanding the API Response Structure

When you make a successful request to the /v1/scrape endpoint with "extract" in formats, or to the /extract endpoint, the API returns a JSON response.

The typical structure for a successful synchronous operation (or a completed asynchronous one retrieved via status check or SDK polling) includes:

  • success: A boolean flag, typically true if the extraction process completed without critical errors.
  • data: An object containing the extracted structured data. The structure of this object depends on whether you used a schema or a prompt:
    • If a schema was provided, data will conform to that schema.
    • If only a prompt was provided, data will have a structure determined by the LLM based on the prompt.

For asynchronous jobs, the initial response might contain a job_id, and status checks will return fields like status and potentially partial results or the final data upon completion.

Commentary:

A consistent response structure is crucial for reliable API integration. The success flag provides a clear indication of whether the core operation completed without fatal errors. The actual extracted data resides within the data field. For asynchronous operations, additional fields like status and job_id will be present, indicating the job's progress. Developers should always check the success flag before attempting to process the data field.

Asynchronous Operations: Job Submission

6.1 Submitting Jobs Asynchronously

The /extract endpoint supports asynchronous operations, which is crucial when dealing with multiple URLs, domain crawling, or web search enabled, as these tasks can take time.

  • API Behavior: When initiating an asynchronous job (e.g., by using specific API parameters or SDK methods like async_extract), the API typically responds quickly with a job_id.
  • SDK Behavior:
    • The standard extract methods in the Python and Node.js SDKs usually handle polling automatically by default, waiting until the job is complete and returning the final result.
    • SDKs also provide explicit asynchronous methods (e.g., async_extract in Python, asyncExtract in Node.js) that return the job_id immediately, allowing for manual status checks.

Commentary:

Asynchronous processing is essential for long-running tasks like crawling entire domains or performing complex extractions, especially with web search enabled. Returning a Job ID immediately allows the client application to remain responsive without waiting potentially minutes for the operation to complete. The client can then poll for the status or use webhooks (if supported by the API, though not mentioned in notes) to get notified upon completion. This is a standard pattern for handling potentially slow API operations.

Checking Asynchronous Job Status

6.2 Monitoring Asynchronous Job Progress

Once you have a job_id from an asynchronous /extract request, you can check its status:

  • Manual Polling (API/SDK): Use the Job ID with a dedicated status check mechanism. The notes suggest using the /extract/ endpoint (likely a GET request with the Job ID, e.g., GET /v1/extract/{job_id}) or specific SDK functions:
    • Python: app.get_extract_status(job_id)
    • Node.js: app.getExtractStatus(job_id)
  • Automatic Polling (SDK Default): As mentioned, the default SDK extract methods often hide the polling complexity.

Status information for jobs (in progress or completed) is typically available for 24 hours.

Python Example (Manual Status Check):

from firecrawl import FirecrawlApp

app = FirecrawlApp(
    api_key="fc-YOUR_API_KEY"
)

# Assume extract_job = app.async_extract(...) was called earlier
job_id = extract_job.job_id 

# Get the status
job_status = app.get_extract_status(job_id)

print(job_status)
# Example output for a completed job:
# {
#     "status": "completed",
#     "progress": 100,
#     "results": [{ "url": "https://docs.firecrawl.dev", "data": { ... } }]
# }

Commentary:

Polling is a common method for checking the status of asynchronous jobs. The client periodically queries a status endpoint using the Job ID. The frequency of polling should be managed carefully to avoid excessive API calls (consider exponential backoff). The SDK methods get_extract_status / getExtractStatus abstract this polling logic, simplifying development. The 24-hour limit for status checks implies that results are stored temporarily and developers should retrieve and store them permanently if needed beyond that window.

Possible Asynchronous Job Statuses

6.3 Understanding Job Status Values

When checking the status of an extraction job, the response will include a status field indicating the current state. Possible values include:

  • processing: The job is currently running.
  • completed: The extraction finished successfully. The results should be available.
  • failed: An error occurred during processing. Data extraction may be incomplete or unavailable.
  • cancelled: The job was cancelled by the user.

Example JSON for a Pending Job Status:

{
  "success": true, 
  "data": [], 
  "status": "processing",
  "expiresAt": "2025-01-08T20:58:12.000Z" 
}

Example JSON for a Completed Job Status:

{
  "success": true,
  "data": {
      "company_mission": "...",
      "supports_sso": false,
      "is_open_source": true,
      "is_in_yc": true
    },
  "status": "completed",
  "expiresAt": "2025-01-08T20:58:12.000Z"
}

The expiresAt field indicates when the job status/results might no longer be available.

Commentary:

These status values represent the typical lifecycle of an asynchronous task. processing indicates work is ongoing. completed signifies success. failed indicates an error occurred, requiring investigation (checking logs or error messages if provided in the status response). cancelled implies user intervention. Robust applications should handle each status appropriately, potentially retrying failed jobs or alerting users.

Python SDK Examples

7.1 Integrating with Python

Firecrawl provides a Python SDK (firecrawl-py) for easier integration. Here are examples demonstrating common /extract use cases:

Initialization:

from firecrawl import FirecrawlApp
app = FirecrawlApp(api_key='your_api_key')

Extraction with Schema (using Pydantic):

from pydantic import BaseModel, Field

class ExtractSchema(BaseModel):
    company_mission: str
    supports_sso: bool
    is_open_source: bool
    is_in_yc: bool

data = app.extract(
    urls=[
        'https://docs.firecrawl.dev/*',
        'https://firecrawl.dev/',
        'https://www.ycombinator.com/companies/'
    ],
    params={
        'prompt': 'Extract the company mission, whether it supports SSO, whether it is open source, and whether it is in Y Combinator from the page.',
        'schema': ExtractSchema.model_json_schema(),
    }
)
print(data)

Extraction without Schema (Prompt-Only):

from firecrawl import FirecrawlApp
app = FirecrawlApp(api_key='your_api_key')

Known Limitations and Beta Status

8.1 Current Limitations (Beta Status)

The /extract feature is currently in Open Beta. As such, users should be aware of some known limitations:

  1. Large-Scale Site Coverage: Attempting to extract data from extremely large websites (e.g., all products on Amazon) in a single request is not yet fully supported or reliable.
  2. Complex Logical Queries: Highly complex or nuanced queries requiring deep logical inference (e.g., "find every blog post published exactly in 2025 containing keyword X but not keyword Y") may not perform reliably yet.
  3. Occasional Inconsistencies: Results, especially for large or highly dynamic websites, might exhibit slight variations between runs.
  4. Beta State Implications: As a Beta feature, its functionality, performance characteristics, and API surface may evolve based on feedback and further development.

Refer to the Extract feature page for potential updates on status and limitations.

Commentary:

Acknowledging limitations is crucial for setting user expectations, especially for a feature in Beta.

  1. Large-Scale Coverage: This suggests users should break down very large extraction tasks (e.g., scraping an entire e-commerce catalog) into smaller, more manageable batches.
  2. Complex Logic: The reliance on LLMs means complex, highly specific logical constraints might be difficult to enforce reliably compared to traditional scraping code. Simpler, more direct extraction prompts/schemas are likely more effective currently.
  3. Inconsistencies: This is common with LLM-based systems and dynamic websites. Developers should implement validation and potentially retry mechanisms or be prepared for some variability in results.
  4. Beta Status: Users should anticipate potential API changes, performance fluctuations, and bugs. It's generally advisable to use beta features with caution in critical production systems.

Experimental and Alpha Capabilities

8.2 Experimental and Alpha Features

Beyond the general Beta status, certain specific capabilities within the Extract feature are flagged as experimental or alpha:

  • Wildcard Domain Crawling (/*): As mentioned previously, using the /* pattern with the /extract endpoint to crawl entire domains is considered experimental.
  • URL-less Extraction: The ability to use the /extract endpoint with only a prompt (and optionally schema) without providing any urls is currently in Alpha. This is useful for research-like queries where the target source isn't a specific URL but rather a concept the system should find information about (potentially using web search implicitly).

Users should treat these features with extra caution, anticipate potential instability or changes, and consult the Firecrawl Documentation for the latest status.

Commentary:

Features flagged as 'Experimental' or 'Alpha' carry higher risk and uncertainty than Beta features. Wildcard crawling (/*) and URL-less extraction are powerful capabilities but likely require further refinement and testing. Developers using these should have fallback strategies, monitor performance closely, and be prepared for breaking changes or removal of the feature. Providing feedback on these experimental features is often valuable to the service provider.
