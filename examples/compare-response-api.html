Compare OpenAI APIs

This task involves creating a detailed comparison between OpenAI's Chat Completion API and the latest Response API, highlighting their differences, use cases, and best practices. It includes providing JavaScript code examples for interacting with both APIs and managing chat history effectively. The goal is to help users decide which API to use based on their specific application needs.

Document Purpose

1.1 Purpose of the Document

This document provides a comprehensive comparison between OpenAI's established Chat Completion API (/v1/chat/completions) and its newer Responses API (/v1/responses). Its goal is to clarify the differences in design philosophy, features, and intended use cases, enabling developers, particularly those with experience in JavaScript and Node.js, to choose the most appropriate API for their specific application needs. It covers core technical distinctions, practical applications, migration considerations, interaction examples, and best practices for managing conversation state.

Commentary:

This document serves as a crucial guide for developers navigating OpenAI's evolving API landscape. Understanding the nuances between the established Chat Completion API and the newer, more agent-focused Responses API is essential for making informed architectural decisions. The choice impacts not only immediate implementation details like request/response structure but also long-term considerations such as scalability, maintainability, and the ability to leverage future OpenAI platform enhancements. As OpenAI pushes towards more sophisticated agentic systems, the Responses API represents a strategic direction, offering built-in capabilities that previously required significant custom implementation.

Chat Completion API Overview

1.2 Overview of OpenAI's Chat Completion API

The Chat Completion API is OpenAI's established, industry-standard API for generating model responses based on conversational input.

  • Endpoint: POST https://api.openai.com/v1/chat/completions
  • Core Concept: Takes a list of messages (messages array) representing the conversation history and returns a model-generated message.
  • Input Structure: Primarily uses the messages array, where each message has a role (system, user, assistant, tool) and content. Supports text, image (Vision), and potentially audio inputs depending on the model.
  • Output Structure: Returns a choices array, typically containing one message object with the assistant's response.
  • Key Parameters: model, messages, temperature, max_completion_tokens, tools, tool_choice, response_format (for JSON Mode/Structured Output), stream.
  • Capabilities: Text generation, vision, audio (model-dependent), function/tool calling, structured output (JSON Mode and JSON Schema).
  • State Management: Stateless; requires the developer to manage and resend the conversation history in the messages array for each turn.

It's widely used for chatbots, content generation, and tasks requiring interaction based on conversation history. See the Quickstart guide for more details.

Commentary:

The Chat Completion API has become the de facto standard for interacting with conversational AI models, not just from OpenAI but also from many other providers who offer compatible APIs. Its simplicity and focus on the messages array made it easy to adopt for a wide range of text generation tasks. Its widespread use means extensive community support, examples, and third-party tooling are readily available. However, its stateless nature and lack of built-in support for complex workflows like tool use orchestration necessitated the development of higher-level frameworks or more sophisticated APIs like the Responses API.

Responses API Overview

1.3 Overview of OpenAI's Responses API

The Responses API is OpenAI's newest core API, designed as a flexible, 'agentic API primitive' to build action-oriented applications. It combines the simplicity of Chat Completions with enhanced capabilities.

  • Endpoint: POST https://api.openai.com/v1/responses
  • Core Concept: Takes an input (string or array of items like text, images, files) and potentially a previous_response_id to generate a response, managing state internally.
  • Input Structure: Uses an input parameter which can be a simple string or an array of typed items (input_text, input_image, input_file).
  • Output Structure: Returns a typed response object, often accessed via helpers like response.output_text in the SDK.
  • Key Parameters: model, input, previous_response_id, tools (including built-ins), text.format (for structured output via JSON Schema), stream.
  • Capabilities: Text generation, vision, structured outputs (JSON Schema preferred), function calling, built-in tools (Web search, File search, Computer use), built-in state management.
  • State Management: Built-in via the previous_response_id parameter.
  • Streaming: Uses a predictable, event-driven architecture with distinct 'semantic events'.

OpenAI recommends new users start with the Responses API, especially for workflows involving tool use, code execution (coming soon), and state management. It aims to simplify these complex interactions compared to the Chat Completion API.

Commentary:

The Responses API signals OpenAI's move towards providing more integrated and 'agentic' primitives directly within their platform. By building in features like state management, specific tool integrations (Web Search, File Search, Computer Use), and a more structured streaming mechanism, OpenAI aims to simplify the development of complex, action-oriented applications. This potentially reduces the need for external orchestration frameworks for common agentic patterns. Its design, focusing on 'semantic events' for streaming and typed responses, suggests an emphasis on developer experience and robustness, particularly for applications that programmatically react to different stages of the response generation process. It's positioned as the foundation for future agent capabilities.

Core Purpose and Design

2.1 API Purpose and Design Philosophy

  • Chat Completion API: Designed as a general-purpose conversational AI endpoint. Its philosophy centers on generating the next message in a sequence based on the provided history (messages). It's highly flexible but requires developers to build more complex logic (like state management, multi-step tool use orchestration) on top.
  • Responses API: Designed as an 'agentic API primitive'. Its philosophy is to provide a more integrated foundation for building applications where the AI takes actions, uses tools, and maintains context over multiple turns more seamlessly. It aims to simplify common agentic workflows by building in features like state management and specific tools (Web search, File search, Computer use). OpenAI positions it as the future direction for building agents on their platform.

Commentary:

The fundamental difference lies in the intended scope. Chat Completions is primarily a text generation API centered around conversation turns. Responses is designed as an agent interaction API. It anticipates workflows where the model doesn't just talk but acts – using tools, accessing files, potentially controlling applications ('Computer use'). This shift from conversation to action necessitates changes in state management, tool integration, and even the streaming protocol to better support observing and reacting to the steps an agent takes.

Input Structure Differences

2.2 Input Structure (messages vs input)

  • Chat Completion API: Requires the messages parameter, an array of message objects, each with a role (system, user, assistant, tool) and content. This structure explicitly represents the conversation history.
    {
  "model": "gpt-4o",
  "messages": [
    {"role": "system", "content": "You are helpful."},
    {"role": "user", "content": "Hello!"}
  ]
}
  • Responses API: Uses the input parameter, which can be a simple string or an array of input items. These items are typed (e.g., input_text, input_image, input_file) and represent the data provided for the current turn, not necessarily the entire history (which is managed via previous_response_id).
    {
  "model": "gpt-4o",
  "input": [
    {"role": "user", "content": "Write a story."}
  ]
  // Optionally: "previous_response_id": "resp_abc123"
}
    See guides for Text inputs, Image inputs, and File inputs in the Responses API.

Commentary:

This structural difference is fundamental. messages in Chat Completions directly mirrors a conversation log, making it intuitive for simple chat applications. The input array in Responses is more abstract, representing various forms of input data (text, images, files, tool outputs) that feed into the agent's processing cycle. This structure is better suited for multi-modal inputs and complex interactions involving files or tool results, moving beyond a purely conversational paradigm.

Output Structure Differences

2.3 Output Structure (choices vs output)

  • Chat Completion API: Returns a response object containing a choices array. Each choice includes the generated message (with role, content, tool_calls), finish_reason, and optionally logprobs.
    {
  "id": "chatcmpl-abc...",
  "object": "chat.completion",
  "created": 1677652288,
  "model": "gpt-4o",
  "choices": [
    {
      "index": 0,
      "message": {
        "role": "assistant",
        "content": "Hello there! How can I help?"
      },
      "finish_reason": "stop"
    }
  ],
  "usage": {...}
}
  • Responses API: Returns a typed response object (e.g., Response type in SDKs) which has its own id (e.g., resp_123...). The generated content is typically within an output array containing typed items like output_text or tool calls. SDKs often provide helpers like response.output_text for easy access.
    {
  "id": "resp_67b73f69...",
  "object": "response",
  "created": 1722987012,
  "model": "gpt-4o",
  "output": [
    {
      "id": "msg_67b73f69...",
      "type": "message",
      "role": "assistant",
      "content": [
        {
          "type": "output_text",
          "text": "Hello there! How can I help?",
          "annotations": []
        }
      ]
    }
  ],
  "usage": {...}
}

Commentary:

The shift from a choices array containing a message to a more structured output array with typed content parts (output_text, tool calls, etc.) in the Responses API reflects its agentic nature. The output isn't just a single text response but potentially a collection of actions or results generated by the agent. The inclusion of a unique id for the response object itself (resp_...) is crucial for the built-in state management mechanism.

Streaming Differences

2.4 Streaming Mechanism (Token Stream vs Semantic Events)

  • Chat Completion API: When stream: true, it returns a stream of Server-Sent Events (SSEs). Each event contains a chat.completion.chunk object with a delta field. The delta contains incremental changes, typically appending tokens to the content or providing parts of tool_calls. Reconstructing the full message or tracking state requires manual client-side logic.
    • See guides: Streaming responses, Streaming function calls, Streaming structured output.

  • Responses API: Also uses SSEs when stream: true, but emits distinct semantic events. These events signal specific stages or changes in the response generation process (e.g., response.created, response.output_text.delta, response.tool_call.started, response.completed). This event-driven architecture is designed to be more predictable, easier to integrate, and type-safe.

    event: response.created
data: {...}

event: response.output_item.added
data: {...} // e.g., a message item

event: response.content_part.added
data: {...} // e.g., an output_text part

event: response.output_text.delta
data: {"delta": "Hello"}

event: response.output_text.delta
data: {"delta": " world"}

event: response.output_text.done
data: {...}

event: response.content_part.done
data: {...}

event: response.output_item.done
data: {...}

event: response.completed
data: {...} // includes final status and usage

    OpenAI explicitly recommends using the Responses API for streaming due to its improved design.

Commentary:

The streaming mechanism is a significant differentiator, especially for user experience in real-time applications and for developers building reactive systems. Chat Completion's token-by-token stream is simple but requires parsing and state management on the client-side to reconstruct messages or identify tool calls. Responses API's semantic events provide a much clearer, structured view of the generation process (e.g., 'tool call started', 'text delta arrived', 'response complete'). This event-driven approach simplifies client-side logic, improves type safety, and makes it easier to react to specific stages of the agent's execution, like displaying a 'searching web...' indicator when a web_search tool event occurs.

Built-in Tool Differences

2.5 Built-in Tool Support

  • Chat Completion API: Supports defining custom tools (currently only function type). The developer provides the schema for the functions the model can call, and the model generates the arguments. The developer's application code is responsible for executing the function and returning the result to the model.
  • Responses API: Supports custom tools (functions) similar to Chat Completions. Crucially, it also offers built-in tools managed by OpenAI:
    • Web search (web_search_preview)
    • File search (for Retrieval-Augmented Generation - RAG)
    • Computer use (computer_use_preview) These built-in tools simplify workflows that require external information retrieval or interaction, as OpenAI handles the execution. Code Interpreter is also planned.

Commentary:

Built-in tools are a major advantage of the Responses API for specific use cases. While Chat Completions allows defining custom functions/tools, implementing the underlying logic (like performing a web search or interacting with files) remains the developer's responsibility. The Responses API provides ready-to-use implementations for common tasks like web search and file search (RAG), significantly reducing development effort for applications needing these capabilities. The 'Computer use' tool hints at future possibilities for more direct interaction with user environments or applications.

State Management Differences

2.6 State Management (messages vs previous_response_id)

  • Chat Completion API: Is stateless. To maintain conversation context, the developer must manually manage the history and send the entire relevant sequence of messages (user, assistant, system, tool) in every API request. This requires careful handling of token limits, often necessitating strategies like summarization or truncation for long conversations.
    • A common strategy is conversation summarization: generate a summary of past turns and include it in the system prompt instead of all messages.
  • Responses API: Has built-in state management. To continue a conversation, the developer simply passes the id of the previous response object in the previous_response_id parameter of the new request. OpenAI uses this ID to retrieve the necessary context and maintain the conversation state internally. This significantly simplifies managing multi-turn interactions.

Commentary:

State management is often a pain point in building conversational AI. Chat Completion's manual approach offers maximum flexibility but requires careful implementation to handle context window limits, potentially involving summarization or other truncation strategies. Responses API's previous_response_id offers significant convenience by offloading history management to OpenAI. This simplifies application logic but might offer less fine-grained control over exactly what context is preserved or how it's compressed compared to manual methods. The choice depends on whether the developer prioritizes convenience or control.

Structured Output Differences

2.7 Structured Output Support (JSON Mode vs JSON Schema)

Both APIs support mechanisms for requesting structured JSON output, moving beyond plain text responses. However, the preferred method and parameter names differ slightly.

  • Chat Completion API:
    • JSON Mode (Legacy): Activated by setting response_format: { "type": "json_object" }. Requires prompting the model to output JSON. Does not guarantee valid JSON or adherence to a specific structure.
    • Structured Output (JSON Schema - Preferred): Activated by response_format: { "type": "json_schema", "json_schema": { "schema": {...}, "strict": true/false } }. Requires providing a JSON Schema. Guarantees schema-adherent JSON output in strict mode (model-dependent).
  • Responses API:
    • Uses the text.format parameter. The preferred method is using JSON Schema: text.format: { "type": "json_schema", "json_schema": { "schema": {...} } }. This aligns with the API's focus on structured interaction.

Using JSON Schema (json_schema) is strongly recommended over the older JSON Mode (json_object) in both APIs for reliable structured data extraction or generation.

Commentary:

Both APIs now offer robust ways to get structured JSON output, which is critical for reliable integration with application logic. The older 'JSON Mode' (json_object) was less reliable as it relied heavily on prompting and didn't guarantee schema adherence. The introduction of JSON Schema support (json_schema) in both APIs, especially with strict mode, provides a much stronger guarantee of valid, schema-compliant JSON output. The Responses API seems to favor the json_schema approach via its text.format parameter, aligning with its focus on reliable, structured interactions needed for agentic workflows.

Model Availability Differences

2.8 Model Availability and Compatibility

OpenAI aims to add new models to both APIs whenever possible. However, there might be differences:

  • General Models: Models like gpt-4o are available on both APIs.
  • Specialized Models: Some models, particularly those relying heavily on built-in tools (like future 'Computer use' models) or involving complex internal multi-turn generation (like o1-pro), might only be available via the Responses API.
  • Parameter Support: Newer models (e.g., o-series) might have slightly different parameter support across the APIs (e.g., reasoning_effort vs reasoning.effort). The max_tokens parameter is deprecated in Chat Completions (use max_completion_tokens) and not compatible with o1 models.

Developers should consult the specific model documentation to confirm API support and compatible parameters for the desired model.

Commentary:

Model availability is a practical constraint. While OpenAI aims for parity, the reality is that cutting-edge models or those tightly integrated with specific platform features (like built-in tools) might debut or only be available on the Responses API. This could be a deciding factor if a specific model capability (e.g., advanced reasoning in o1-pro, or a future model using 'Computer use') is required. Developers should always check the specific model documentation for API compatibility.

Use Case: Chatbots

3.1 Chatbots and Conversational Interfaces

Both APIs are suitable for building chatbots and conversational UIs.

  • Chat Completion API: The traditional choice. Its messages structure directly maps to conversation turns. Requires manual state management (sending history with each request) or implementing summarization strategies for long conversations.
  • Responses API: Offers built-in state management via previous_response_id, simplifying the development of multi-turn conversations. Its semantic streaming events can also enhance the UI by providing clearer feedback on the generation process.

The choice may depend on the complexity of the conversation and whether the developer prefers manual control over state (Chat Completions) or built-in convenience (Responses).

Commentary:

Chatbots remain a primary use case for LLM APIs. While both APIs can power chatbots, the Responses API's built-in state management (previous_response_id) can significantly simplify development by removing the need for manual history tracking in the application code. For simple bots, Chat Completions is sufficient, but for more complex conversational agents maintaining long contexts, Responses offers convenience.

Use Case: Data Extraction

3.2 Data Extraction and Structured Output

LLMs can be used to extract structured data from text. Both APIs support this effectively using their structured output features.

  • Method: Use the response_format (Chat Completions) or text.format (Responses) parameter with type: "json_schema" and provide a JSON Schema defining the desired output structure.
  • Reliability: Using json_schema (especially with strict: true where supported) provides high confidence that the output will be valid JSON conforming to the specified schema, although the correctness of the extracted values still depends on the model's understanding.
  • Example Use Case: Extracting product details, contact information, or key entities from unstructured text documents.

This is preferable to the older, less reliable json_object mode or trying to parse unstructured text output.

Commentary:

Structured data extraction is a powerful application of LLMs, transforming unstructured text into usable data. Both APIs now excel here thanks to JSON Schema support. This is far more reliable than prompt-based JSON formatting or regex. The guaranteed schema adherence (in strict mode) makes it feasible to directly integrate LLM output into databases, APIs, or other automated workflows. This capability is crucial for tasks like parsing invoices, extracting information from emails, or categorizing user feedback.

Use Case: Agentic Workflows

3.3 Agentic Workflows and Tool Use

Agentic workflows involve LLMs performing sequences of actions, potentially using tools, to achieve a goal. This often involves loops of planning, action, and reflection.

  • Chat Completion API: Can be used to build agents, but requires the developer to implement the orchestration logic: deciding when to call tools, parsing tool_calls from the response, executing the tools, and sending results back to the model. Frameworks like LangChain often help manage this complexity.
    • Example: The websearch example combines multiple steps (decide search, pick domains, rate results, scrape, answer) orchestrated around Chat Completion calls.
  • Responses API: Designed to simplify agentic workflows. It offers:
    • Built-in Tools: Web search, File search, Computer use reduce the need for custom tool implementation.
    • Integrated Tool Handling: The API manages aspects of the tool use lifecycle.
    • State Management: Simplifies tracking progress across multiple steps.

For complex agents involving multiple tools or steps, the Responses API offers a more integrated and potentially simpler development path.

Commentary:

Agentic workflows represent the cutting edge of LLM applications, moving beyond simple Q&A to tasks involving planning, tool use, and interaction with external systems. The Responses API is explicitly designed for this, offering built-in tools and state management that streamline agent development. While agents can be built using Chat Completions, it requires significantly more orchestration logic within the application (often using frameworks like LangChain or LlamaIndex). The 'Chain' and 'Agent' concepts described in the notes illustrate these patterns, involving multiple LLM calls, decision-making steps, and interactions with tools like web search.

Use Case: RAG

3.4 Document Search and Retrieval (RAG)

Retrieval-Augmented Generation (RAG) involves retrieving relevant information from external documents (e.g., a knowledge base, PDFs) and providing it to the LLM as context to answer a query.

  • Chat Completion API: RAG is implemented manually. The application searches an external vector database or index, retrieves relevant document chunks, and inserts them into the messages array (often in the system prompt or as user messages) before calling the API.
  • Responses API: Offers a built-in File search tool. This allows developers to upload files to OpenAI and have the API handle the retrieval and injection of relevant context automatically when the tool is invoked. This simplifies the RAG implementation by abstracting away the indexing and retrieval steps.

While manual RAG with Chat Completions offers more control over the retrieval process, the Responses API's built-in tool provides a potentially faster path to implementing RAG.

Commentary:

Retrieval-Augmented Generation (RAG) is a key technique for grounding LLM responses in specific external knowledge, reducing hallucinations and providing up-to-date information. While Chat Completions can be used for RAG (by retrieving documents externally and inserting their content into the messages prompt), the Responses API's built-in 'File search' tool aims to streamline this process significantly. By managing the file indexing and retrieval, it potentially simplifies the implementation of RAG systems, especially for developers new to the concept.

Use Case: Streaming

3.5 Streaming Applications

Streaming responses is essential for applications requiring real-time feedback, like chatbots or code generation assistants.

  • Chat Completion API: Supports streaming (stream: true) via token-based SSEs (chat.completion.chunk with delta). Requires client-side logic to assemble the final response and interpret the stream.

    • Python Example (Concatenating Content):

      from openai import OpenAI
client = OpenAI()

stream = client.chat.completions.create(
    model="gpt-4o",
    messages=[{"role": "user", "content": "Say 'hi' ten times."}],
    stream=True,
)

full_response = ""
for chunk in stream:
    if chunk.choices and chunk.choices[0].delta.content is not None:
        content = chunk.choices[0].delta.content
        print(content, end="")
        full_response += content
  • Responses API: Also supports streaming (stream: true) but uses semantic events via SSEs. This provides a more structured stream that is easier to parse and react to different phases of generation (e.g., text deltas, tool calls, completion).

OpenAI explicitly recommends the Responses API for streaming due to its improved, event-driven architecture, which simplifies integration and enhances type safety.

Commentary:

Streaming is crucial for user-perceived performance in interactive applications. Both APIs support streaming, but the Responses API's semantic event model offers advantages for building sophisticated UIs. Developers can listen for specific events (e.g., tool_call.start, output_text.delta, response.completed) to provide more granular feedback to the user about what the AI is doing, rather than just displaying incrementally appearing text. This richer feedback can significantly improve the user experience for complex or long-running requests.

When to Use Chat Completions

4.1 Scenarios Favoring Chat Completion API

Consider using the Chat Completion API (/v1/chat/completions) if:

  1. Existing Project: You have an existing application successfully using this API, and migration offers limited benefits.
  2. No Need for Built-in Tools: Your application does not require web search, file search (RAG), or computer use capabilities provided natively by the Responses API.
  3. Prefer Manual State Control: You prefer or require fine-grained control over conversation history management, including custom summarization or truncation logic.
  4. Simpler Use Cases: Your primary need is text generation, simple conversation, or basic function calling where the orchestration logic is manageable.
  5. Industry Standard: You prioritize using the most widely adopted and understood API structure, potentially for compatibility with other tools or services mimicking OpenAI's API.
  6. Maximum Flexibility: You need the flexibility to implement complex, custom agentic loops or state management strategies not directly supported by the Responses API's built-in features.

Commentary:

Stick with Chat Completions if your project is mature, doesn't require the specific built-in tools of the Responses API, and you have already invested in building robust state management and tool orchestration logic. Its stability and vast ecosystem are valuable. It's also the safe choice if you need maximum control over the context sent to the model or if you rely heavily on third-party tools and frameworks tightly coupled with the Chat Completions API structure.

When to Use Responses API

4.2 Scenarios Favoring Responses API

Consider using the Responses API (/v1/responses) if:

  1. New Project: You are starting a new project, especially one involving agentic capabilities. OpenAI recommends new users start here.
  2. Need Built-in Tools: Your application requires web search, file search (RAG), or computer use, and you want to leverage OpenAI's integrated solutions.
  3. Simplified State Management: You want to simplify multi-turn conversation handling using the previous_response_id mechanism.
  4. Agentic Workflows: You are building complex agents involving tool use, planning, and potentially code execution (when available), and want an API designed for these tasks.
  5. Improved Streaming: You need robust streaming with clearer state signaling (semantic events) for better UI feedback or backend processing.
  6. Future Capabilities: You want to easily adopt future OpenAI platform enhancements, as the Responses API is positioned as the foundation for these.
  7. Specific Model Requirements: You need to use a model or feature (like o1-pro or certain reasoning parameters) that is only available or better supported via the Responses API.

Commentary:

The Responses API is compelling for new projects, especially those aiming for more complex, agent-like behavior. The built-in tools and state management can significantly accelerate development. If your application heavily relies on RAG, web search, or anticipates using future capabilities like Code Interpreter or Computer Use, starting with the Responses API aligns you with OpenAI's strategic direction and potentially simplifies future integrations. The improved streaming mechanism is also a strong reason if user experience with real-time feedback is critical.

Migration Considerations

4.3 Migration Considerations for Existing Projects

If considering migrating an existing project from the Chat Completion API to the Responses API, be aware of the following:

  1. API Structure: Request parameters (messages vs input) and response structures (choices vs output) are different, requiring code changes in how you call the API and process results.
  2. State Management: You'll need to replace manual history management (building the messages array) with logic to store and use the previous_response_id from the Responses API output.
  3. Streaming: If using streaming, the client-side logic must be updated to handle semantic events instead of raw token deltas.
  4. Tool/Function Calling: The API shape for defining tools and handling tool calls differs. Check the respective documentation for implementation changes.
  5. Structured Output: Parameter names differ (response_format vs text.format), although the underlying JSON Schema mechanism is similar.
  6. Testing: Thorough testing is required to ensure functional equivalence and handle potential behavioral differences between the APIs or underlying model interpretations.

Migration involves non-trivial effort and should be justified by the benefits offered by the Responses API for the specific application (e.g., need for built-in tools, simplified state, improved streaming).

Commentary:

Migrating from Chat Completions to Responses is not a simple drop-in replacement due to the fundamental differences in request/response structure, state management, and streaming. Key considerations include refactoring API call logic, adapting state management (from manual messages construction to using previous_response_id), handling the different output structures, and potentially updating streaming logic to work with semantic events instead of token deltas. Tool/function calling implementation will also likely require changes. Thorough testing is crucial. Given OpenAI's plan to eventually deprecate the Assistants API in favor of Responses, understanding these migration paths might become relevant for Assistants API users as well.

JS Example: Chat Completion

5.1 Chat Completion API Example (Node.js with OpenAI SDK)

The notes provide a conceptual example using curl to interact with a Node.js backend that presumably uses the OpenAI SDK. While direct SDK code isn't shown for this specific API in the notes, the interaction pattern is illustrated.

Conceptual Interaction (Client -> Node.js Backend):

A client (e.g., a web frontend or another service) sends a POST request to a Node.js API endpoint.

curl -X POST http://localhost:3000/api/chat \
-H "Content-Type: application/json" \
-d '{"messages":[{"role":"user","content":"Hello from client!"}]}'

Conceptual Node.js Backend Logic (using openai package):

// Assuming setup with Express, Hono, or similar
// import { OpenAI } from 'openai';
// const openai = new OpenAI({ apiKey: process.env.OPENAI_API_KEY });

app.post('/api/chat', async (req, res) => {
  try {
    const userMessages = req.body.messages; // Get messages from client

    // --- Add system prompt and potentially history --- 
    const messagesForApi = [
      { role: 'system', content: 'You are a helpful assistant.' },
      ...userMessages // Append client messages
      // Potentially load more history from DB here
    ];

    const completion = await openai.chat.completions.create({
      model: 'gpt-4o', // Or other desired model
      messages: messagesForApi,
      // Add other parameters like temperature, max_tokens, stream, etc.
    });

    // Send response back to client
    res.json(completion.choices[0].message);

  } catch (error) {
    console.error('Error calling OpenAI:', error);
    res.status(500).json({ error: 'Failed to get completion' });
  }
});
  • Key SDK Method: openai.chat.completions.create(requestBody)
  • Request Body: Contains model, messages, and other optional parameters from the API reference.
  • Source Code Reference: The notes mention example code in a GitHub repository: https://github.com/i-am-alice/3rd-devs/tree/main/streaming (within the sdk folder, though the link points to streaming).
  • Recommended SDK: Use the official OpenAI Node.js SDK.

Commentary:

While the notes lack direct JavaScript SDK examples for the latest OpenAI SDK usage, the principles remain the same. You'd use the openai package, instantiate a client, and call the appropriate method (client.chat.completions.create). The key is correctly constructing the request object, including the model and messages array. For a Node.js backend, this logic would typically reside in an API route handler (like in Express, Hono, or Nest.js) that receives user input, constructs the messages array (potentially retrieving history from a database), calls the OpenAI API, and sends the response back to the client.

To get structured JSON output conforming to a specific schema using the OpenAI Node.js SDK, you need to set the appropriate parameter in the API call.

1. Define your JSON Schema: Create a standard JSON Schema object describing the desired output structure.

const mySchema = {
  type: 'object',
  properties: {
    name: { type: 'string', description: 'Person\'s full name' },
    age: { type: 'integer', description: 'Person\'s age' },
    isStudent: { type: 'boolean', description: 'Whether the person is a student' }
  },
  required: ['name', 'age']
};

2. Include it in the API Call:

  • For Chat Completion API: Use the response_format parameter.

    const completion = await openai.chat.completions.create({

  text: {

JS Example: Streaming

5.4 Streaming Responses in JavaScript

To handle streaming responses using the OpenAI Node.js SDK, set stream: true in the request. The SDK method will typically return an async iterator.

1. Chat Completion API Streaming: Iterate through chunks and accumulate the delta.content.

async function streamChatCompletion() {
  const stream = await openai.chat.completions.create({
    model: 'gpt-4o',
    messages: [{ role: 'user', content: 'Tell me a very short story.' }],
    stream: true,
  });

  let fullResponse = "";
  console.log('Streaming response:');
  for await (const chunk of stream) {
    const content = chunk.choices[0]?.delta?.content || '';
    process.stdout.write(content); // Write chunk to console in real-time
    fullResponse += content;
  }
  console.log('\n--- End of Stream ---');
  return fullResponse;
}
  • The Python examples in the notes demonstrate this logic clearly.
  • You might also receive tool_calls deltas within the stream.
  • Include stream_options: { include_usage: true } to get usage stats in the final chunk.

    }

Streaming in Node.js involves handling the asynchronous nature of Server-Sent Events (SSEs). The OpenAI Node.js SDK typically returns an async iterator when stream: true. You loop through this iterator (for await...of) to process each chunk or event as it arrives. For Chat Completions, you'll concatenate delta.content. History: Responses API (Built-in)

6.2 Responses API: Using previous_response_id

The Responses API offers built-in state management, simplifying conversation history handling.

  • Mechanism:

    1. Make the first call to the Responses API without previous_response_id.
    2. The API returns a response object containing a unique id (e.g., resp_abc123).
    3. Store this id.
    4. For the next turn in the conversation, include this stored ID in the previous_response_id parameter of the request. ```javascript // First call const response1 = await openai.responses.create({ model: 'gpt-4o', input: [{ role: 'user', content: 'What is the capital of France?' }] }); const responseId1 = response1.id; // Store responseId1 (e.g., in user session or DB)

    // Second call (continuing conversation) const response2 = await openai.responses.create({ model: 'gpt-4o', input: [{ role: 'user', content: 'What is its population?' }], previous_response_id: responseId1 // Link to the previous turn }); const responseId2 = response2.id; // Store responseId2 for the next turn... ```

  • Benefit: The developer does not need to manually construct and send the entire message history. OpenAI uses the previous_response_id to manage the context internally.

Commentary:

The previous_response_id mechanism in the Responses API is a significant simplification for developers. It abstracts away the complexity of manually assembling and potentially compressing the conversation history. OpenAI handles the context retrieval based on the provided ID. This is particularly beneficial for rapid development and for applications where complex manual history management isn't necessary. However, it offers less transparency and control compared to the manual approach; developers rely on OpenAI's internal logic for context management.

History: Summarization Strategies

6.3 Summarization Strategies for Long Conversations

When conversations become too long to fit within the model's context window (especially relevant for manual history management with Chat Completions), summarization is a key strategy.

  • Problem: Sending the full history consumes tokens (increasing cost) and can exceed model limits.
  • Solution: Instead of sending all past messages, generate a summary of the conversation up to a certain point.
  • Implementation (thread example):
    1. After a few turns, use an LLM (potentially a cheaper one like gpt-4o-mini) to summarize the existing messages array.
    2. In subsequent requests, replace the older messages with this summary, typically placed within the system prompt or as a condensed assistant message, followed by the most recent user message.

Commentary:

Summarization is a practical technique to manage context window limitations and potentially reduce costs, especially with the Chat Completion API or when implementing custom state management. The key challenge is balancing information retention with brevity. Simple truncation (dropping old messages) is easy but loses context. Summarization aims to preserve the gist of the conversation. This can be done programmatically or, meta-cognitively, by using another LLM call (often with a cheaper, faster model) specifically tasked with summarizing the history. The quality of the summary directly impacts the main model's ability to maintain context effectively.

History: Database Storage

6.4 Database Schema for Storing Conversations

Storing conversation history persistently is essential for most applications.

  • Purpose: Allows users to continue conversations later, provides context for state management (especially manual), and enables logging/auditing.
  • Recommended Storage: Relational databases like PostgreSQL or NoSQL databases like MongoDB are suitable.

  • Example Schema Structure: A table (e.g., conversation_messages) could include fields like:

    • message_id (Primary Key, e.g., UUID)
    • thread_id or conversation_id (Foreign Key linking messages in the same conversation, Indexed)
    • user_id or session_id (Identifier for the user/session)
    • role (String: user, assistant, system, tool)
    • content (Text: The actual message content)
    • timestamp (Timestamp, Indexed)
    • openai_response_id (String, Nullable: Store the id from Responses API if used)
    • metadata (JSONB/TEXT: Optional, for storing model name, token counts, latency, etc.)

This structure allows retrieving the history for a specific conversation (thread_id) ordered by timestamp to reconstruct the messages array for the Chat Completion API or to find the latest openai_response_id for the Responses API.

Commentary:

A well-designed database schema is crucial for persisting conversations, enabling users to resume interactions later and providing data for analysis or fine-tuning. The suggested schema provides a good starting point. Key considerations include indexing (especially on thread_id and timestamps for efficient retrieval), handling potentially large message content (using appropriate data types like TEXT), storing metadata (like model used, latency, token counts, finish reason), and ensuring compliance with data privacy regulations (e.g., GDPR, CCPA) if storing user conversations.

Best Practices

7.3 Best Practices for API Integration

Regardless of which API you choose, follow these best practices:

  1. Use Official SDKs: Utilize official libraries (OpenAI Node.js SDK) for easier integration, type safety, and handling API details.
  2. Manage API Keys Securely: Store API keys in environment variables or secure secret management systems. Do not hardcode them in your source code.
  3. Implement Robust Error Handling: Handle potential network errors, API errors (e.g., rate limits, invalid requests), and timeouts gracefully.
  4. Manage State Appropriately: Choose a state management strategy (manual history + DB for Chat Completions, previous_response_id + DB for Responses) and implement it reliably.
  5. Optimize for Cost and Latency: Monitor token usage. Consider summarization, using cheaper models for simpler tasks, or caching responses where applicable.
  6. Structure Prompts Effectively: Use clear instructions, system prompts, and potentially few-shot examples. For complex prompts, consider organizing them outside main code logic.
  7. Leverage Structured Output: Use JSON Schema (json_schema) for reliable data extraction or function argument generation instead of parsing text.
  8. Monitor and Log: Use tools like LangFuse or LangSmith to monitor LLM calls, track prompts/responses, debug issues, and manage prompt versions.
  9. Consider Alternatives: Don't use LLMs for tasks easily solvable programmatically (e.g., simple data manipulation, regex). Evaluate if traditional search or databases suffice before implementing complex LLM solutions.

Commentary:

Beyond the API choice, successful integration involves robust error handling (network issues, API errors, rate limits), cost management (monitoring token usage, potentially using cheaper models for certain tasks like summarization), security (protecting API keys, handling user data responsibly), and observability (using tools like LangFuse or LangSmith to track prompts, responses, latency, and costs). Prompt engineering remains crucial for getting desired behavior, and managing prompts effectively (versioning, testing) is key for maintainability.
